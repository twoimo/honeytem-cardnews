# Honeytem 카드에서 무음 릴스 초안 내보내기

`reel`은 기존 Honeytem의 **무결성 검증을 통과한 완료 패키지**를 입력으로 받는 선택 기능입니다. 다른 저장소나 카드 디자인/운영 규칙은 변경하지 않습니다. 표지 → 상품 번호 순서로 정지 카드를 배치한 무음 H.264 MP4와 검증용 출처 manifest를 만듭니다. 음악 수집, 외부 통신, 계정 연결, 예약/자동 발행 기능은 없습니다.

## 실행

Python 의존성 외에 로컬 `ffmpeg`(`libx264` 포함), `ffprobe`가 PATH에 있어야 합니다. 자동 설치나 다운로드는 하지 않습니다. 도구가 없거나 실패하면 성공한 결과처럼 처리하지 않습니다.

```bash
# RUN_DIR는 honeytem build가 반환한 기존 완료 run 디렉터리입니다.
# 출력 디렉터리는 아직 존재하지 않아야 하며 source run과 별개여야 합니다.
honeytem reel "$RUN_DIR" --output output/reel-review --durations 3 --fps 30
honeytem verify-reel output/reel-review

# cover와 상품 3개 각각의 길이. 개수는 실제 카드 수와 같아야 합니다.
honeytem reel "$RUN_DIR" --output output/reel-review-alt \
  --durations 2.5 3.5 3 4 --fps 30 \
  --padding-color '#F5F4F0' --vertical-align center
```

- 기본 캔버스: 1080×1920, 카드당 3초, 30fps, 흰색, 수직 중앙 정렬
- 카드: 기존 1080×1350 RGB PNG를 **원래 크기 그대로** 붙입니다. 확대/축소, 크롭, 왜곡, 새 이미지 생성 또는 카드 내부 편집은 하지 않습니다.
- 패딩 색: 기존 팔레트의 흰색 `#FFFFFF`, 오프화이트 `#F5F4F0`, 연회색 `#ECEDEC`, 검정 `#000000`
- 수직 정렬: `top`, `center`, `bottom`; 수평 정렬은 중앙
- Python API에서는 `width`, `height`로 1080×1920~2160×3840 범위의 짝수 픽셀 9:16 캔버스를 지정할 수 있습니다. 카드의 크기는 그대로입니다.
- fps: 정수 1~60. 각 카드 길이: 최소 1프레임 이상, 최대 60초. 전체 요청 길이: 최대 180초. 불리언, NaN, Infinity, 음수, 0, 과도한 값은 거부합니다.
- 길이를 문자열로 받아 decimal → rational로 계산하므로 CLI에서 binary float 누적 오차를 만들지 않습니다.

## 제휴 이미지의 별도 권리 확인

이미지를 카드에 배치할 수 있다는 확인만으로 영상 파생물/트랜스코딩까지 허용되었다고 간주하지 않습니다. 원본의 provenance mode가 `affiliate`인 경우 기본값은 내보내기 거부입니다. 운영자가 해당 원본에 대한 파생 영상/손실 압축 권한을 별도로 확인한 경우에만 `--allow-affiliate-transcoding`을 명시합니다. 이 플래그는 로컬 운영자의 확인 진술이며 권리의 법적 유효성을 독립적으로 증명하지 않습니다.

합성 fixture와 `concept`은 미리보기 제작이 가능하지만 실제 상품 사진이나 판매 승인 결과로 바뀌지 않습니다. 원본의 `approval.json`은 수정/승계하지 않으며 영상은 언제나 `publish_ready=false`입니다.

## 출력과 검증

새 출력 디렉터리는 다음만 포함합니다.

- `reel.mp4`: H.264, CRF 18, medium preset, yuv420p, 무음, 고정 프레임률
- `frames/00.png` 등: 인코딩 전의 정확한 패딩 PNG. 검토 및 원래 카드 픽셀 보존 확인용
- `reel-manifest.json`: 원본 package/fingerprint와 카드별 원본 PNG/RGB 해시, 카드 순서·경계·패딩 PNG 해시, 프레임 계획, 도구 버전, 구현 해시, 정확한 인코더 인수(임시 디렉터리는 placeholder), MP4 SHA-256, ffprobe 검증 결과 및 한계

원본 ZIP, state, 카드와 approval은 쓰지 않습니다. 별도 임시 디렉터리에서 생성/검증한 뒤 결과를 게시하며, 기존 출력은 덮어쓰지 않습니다. 실패한 임시 결과는 제거하고 오류를 반환합니다. 중단 후 남은 lock은 자동으로 지우지 않습니다. 활성 작업이 없는지 확인한 운영자만 정리합니다.

`verify-reel`은 전체 파일 목록, 해시, PNG 크기·패딩 색·원래 카드 RGB 영역, 계획의 일관성, MP4의 실제 디코딩 프레임 수·fps·크기·길이·단일 영상 스트림/무음 여부를 다시 검사합니다. ffmpeg가 0을 반환했다는 이유만으로 성공을 선언하지 않습니다. 잘리거나 잘못된 영상, 누락/추가 파일, symlink는 거부합니다.

명령 결과의 `manifest_sha256`을 별도 신뢰 채널에 보관해 비교하십시오. 파일과 manifest를 함께 교체할 수 있는 공격자가 있다면 내부 해시만으로 작성자를 인증할 수 없습니다. CLI의 `--expected-manifest-sha256`을 사용하면 신뢰된 manifest 해시와 비교할 수 있습니다. ffprobe의 프레임 수 검사는 일반 영상의 의미/미학이나 매 프레임의 상품 진실성을 증명하지 않습니다.

## 수학적 불변식과 증명 범위

카드 수를 n∈[2,6], 정수 fps를 f, 유리수 요청 길이를 dᵢ로 둡니다. 각 dᵢ≥1/f입니다.

1. 누적 프레임 위치 Sₖ=f·Σᵢ₌₁ᵏdᵢ와 경계 Bₖ=⌊Sₖ+1/2⌋, B₀=0을 계산합니다. k번째 카드의 정수 구간은 `[Bₖ₋₁, Bₖ)`이고 프레임 수는 Nₖ=Bₖ−Bₖ₋₁입니다.
2. Sₖ−Sₖ₋₁≥1이므로 Bₖ−Bₖ₋₁≥1입니다. 따라서 모든 카드가 최소 한 프레임을 가집니다.
3. 인접 구간의 끝과 시작이 동일하므로 서로 겹치거나 비어 있는 프레임 번호가 없습니다. 망원합으로 ΣNₖ=Bₙ이며, 최종 영상 길이는 Bₙ/f입니다.
4. 반올림 정의로 −1/2 < Bₖ−Sₖ ≤1/2입니다. 모든 누적 경계에서 시간 오차의 절댓값은 1/(2f) 이하입니다. 카드별 길이를 독립적으로 반올림한 뒤 더하는 방식처럼 오차가 누적되지 않습니다. 개별 카드 길이의 양자화 오차는 최대 1프레임 이내입니다.
5. 예를 들어 f=10, dᵢ=0.15초를 6회 사용하면 Nᵢ는 `[2,1,2,1,2,1]`, 합은 9프레임입니다. 개별 반올림 후 합산하는 12프레임이 아닙니다.
6. 인코더는 각 입력을 Nᵢ프레임에서 자르고 시간축을 정확한 전역 시작 프레임 Bᵢ₋₁로 배치한 뒤 `interleave`합니다. 한 프레임짜리 카드도 유효한 간격을 가집니다. 실제 출력은 별도로 `ffprobe -count_frames`로 확인합니다.
7. 패딩 PNG의 카드 영역에서는 모든 원래 좌표 (i,j)에 대해 C(x+i,y+j)=I(i,j)를 바이트/픽셀 비교합니다. 정수 위치의 native paste 외에 변환을 하지 않기 때문입니다. **이 증명은 인코딩 전 PNG에만 적용됩니다. H.264/yuv420p는 손실 압축/색차 변환이므로 MP4의 RGB 픽셀 동일성을 주장하지 않습니다.**

같은 카드, 코드, 옵션, Pillow/FFmpeg 빌드에서 단일 인코더/필터 스레드, 고정 설정, 임의 시간 metadata 배제로 반복 바이트 일치를 검사합니다. 다른 OS/코덱 빌드의 비트 동일성이나 실제 상품의 시각 품질 비회귀를 보장하지 않습니다.

## 실패/자원 제한

- 외부 프로세스는 shell 없이 argv로 실행하며 입력 프로토콜은 로컬 file로 제한합니다.
- 프로세스별 600초 timeout, stdout+stderr 합계 1 MiB 제한을 실행 중 적용합니다. 오류는 종료 코드와 안전한 필드 설명만 반환하며 원문 stderr나 비밀 경로를 출력하지 않습니다.
- ffmpeg 파일 크기 제한을 255 MiB로 요청하고, 최종 MP4는 256 MiB 이하만 읽고 수용합니다. 크기 제한으로 중단된 영상은 예상 프레임 수와 맞지 않아 실패합니다. 캔버스·카드 수·총 길이에도 상한이 있습니다.
- 로컬 프로그램/OS가 악의적이거나 동시에 파일을 바꾸는 강한 다중 사용자 공격 모델, 비디오 라이브러리 취약점을 완전 방어한다고 주장하지 않습니다.

## 실제 검증과 측정 (2026-10-21)

Linux x86_64, Python 3.12.14, Pillow 12.3.0, FFmpeg/ffprobe 7.1.5 Debian build에서 실제 `libx264` 인코딩했습니다.

- 표지 + 합성 도형 카드 3개, 1080×1920, 30fps, 카드당 3초: 총 12초 / 360프레임
- 독립 3회 내보내기: 7.3045초, 7.4480초, 7.6280초. 중앙값 7.4480초
- 위 시간은 원본 무결성 검사, 패딩 PNG 생성, 인코딩 및 출력 재검증을 포함합니다.
- MP4 143,356 bytes. 3회 MP4와 manifest 해시가 각각 동일했습니다.
- MP4 SHA-256: `19ed1ea1b37feb70f94a50445b3fc2538863586cd94b81b28cd149db20b3d4e8`
- 1·10·29·60fps에서 한 프레임 카드/분수 경계 사례를 실제 인코딩 후 모든 프레임을 디코딩해 카드 순서를 검사했습니다. 작은 합성 테스트 프레임의 오차 검사는 미학이나 실제 상품 충실도의 보증이 아닙니다.
- 디코딩 contact sheet에서 전체 카드·상하 여백·표지/상품 순서를 확인했습니다.
- 단위/통합 테스트는 1,000개의 결정적 임의 duration 조합의 경계 불변식, NaN/무한/불리언, 경로/변조, 누락 도구, 실패 종료, 시간/출력 제한, 별도 제휴 권리 gate를 포함합니다.

기존 저장소에는 비교 가능한 실행형 릴스 인코더가 없었습니다. 위 수치는 새 선택 기능의 관찰값이지 기존 AI 작업보다 빠르다는 주장이나 양적 품질 비회귀 증명이 아닙니다. 카드 build 경로는 reel 모듈을 자동 호출하지 않으며 이 추가 단계는 명시적으로 요청한 경우에만 실행합니다. Mac 성능과 실제 상품 영상 비교는 아직 미측정입니다.
